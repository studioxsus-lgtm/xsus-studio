# Phase 51 — Host operation integration

This module composes the Phase 49 trusted host agent and Phase 50 durable host operation ledger. The ledger acquires the **single outer cross-process execution lock**; the agent uses an intentional pass-through lock inside that protected callback to avoid nested non-reentrant lock deadlocks. It registers a pending operation before physical execution, checks the host fence, records the physical action receipt and marks the ledger applied. Duplicate applied operation IDs do not repeat physical effects. Pending and uncertain operations require reconciliation.

**Security requirements:** `withExclusiveExecutionLock` must be truly cross-process and held across durable ledger updates, host fencing, the physical operation and receipt persistence. All stores must be durable and correctly scoped to the same host/execution identity. Authorization must bind the caller to owner and holder, and host fencing must be enforced by the real host agent, not a separate read followed by an unfenced Docker command. This is an integration of injected contracts, not a real host daemon or deployed executor. Equal-fence distinct operation IDs still require policy authorization and reconciliation; the operation ledger does not provide globally exactly-once side effects. A crash after a physical action but before receipt or applied state remains ambiguous. No live host or PostgreSQL tests were run.
