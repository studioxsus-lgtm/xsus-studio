# Phase 53 — PostgreSQL host lock coordinator

Implements the Phase 51 `withExclusiveExecutionLock(executionId, callback)` interface using a dedicated PostgreSQL session and session-scoped advisory locks. The same connection is held through the callback and the lock is explicitly released before connection release. Keys are namespaced and parameterized. A failed unlock or release fails closed.

**Critical limits:** Session-scoped PostgreSQL advisory locks are **not durable**: a dropped database connection releases the lock even if a host-side action continues. A pooled connection MUST remain pinned; transaction-pooling PgBouncer is incompatible. This implementation does not verify that the session stays alive throughout the physical action, and does not fence a worker after connection loss. Hash-based advisory keys can collide, causing unnecessary serialization. Do not treat this as sufficient cross-host fencing or production-ready exactly-once execution. A host-side durable fencing authority, bounded operations, cancellation, recovery and real PostgreSQL concurrency tests are still required. No live database or Docker commands were run. Tests use mocked clients.
