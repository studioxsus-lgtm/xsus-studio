# Phase 50 — Durable host operation ledger

The host-operation ledger records an operation ID, execution ID, holder, lease fence, operation type and status before invoking a physical action. It requires a cross-process exclusive execution lock and durable store with atomic create-if-absent and compare-and-swap. A completed operation ID is never physically executed twice by this coordinator; pending or uncertain operations are blocked from replay and require reconciliation. Failures after a possible physical side effect are not automatically retried.

**Production limitations:** The durable store and lock are injected interfaces, not implemented database or host primitives. The ledger is not yet wired into `trusted-host-agent.js`. The coordinator cannot guarantee exactly-once physical effects if a host crashes after the side effect but before the durable acknowledgement. Operation IDs must be authenticated and unique per intended action. Cross-host fencing, trusted host identities, receipt integrity, physical outcome reconciliation and real PostgreSQL crash tests remain necessary. Tests use mocks only. No live host, database, migration or deployment was modified.
